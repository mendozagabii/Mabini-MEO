# 🔎 Audit — 2026-11-09 (baseline `ce9a474`)

Method: `npm ci`, `npx tsc --noEmit` (✅ pass), `npm run build` (✅ pass), then ran the
production server and **live-tested** the API with `curl`, plus manual code review.
Findings marked ✅ were reproduced live; 👀 = found by reading code.

## 🔴 CRITICAL — Authentication is effectively non-existent

1. **No session at all.** ✅ `POST /api/auth/login` returns user JSON but sets **no cookie/token**
   (`Set-Cookie` absent). The frontend just flips `isLoggedIn` state (`src/app/App.tsx:288`).
   Login is a UI gate only.
2. **Every API route is unauthenticated.** ✅ Verified live without any login:
   - `GET /api/auth/status` → dumps all users (names, emails, roles)
   - `POST /api/auth/status` → created a `Head Engineer` account (`intruder@test.local`), then logged in with it
   - `POST /api/local-road`, inspections, maintenance, activity-logs → full create/edit/delete/archive
   Role permissions in `App.tsx:597` are client-side only and bypassable via direct API calls.
3. **Default credentials seeded on first run** 👀 (`src/lib/demo-data.ts`):
   `admin/admin123`, `encoder/encoder123`, `inspector/inspector123`, `validator/validator123`
   — publicly visible in the repo, auto-created in `seedUsers()`. ✅ `admin/admin123` works.
4. **Hardcoded default master unlock code `master123`** 👀 (`src/lib/master-password.ts:23`),
   stored in plaintext in `data/master-password.txt` when changed. ✅ Worked live.
5. **Account unlock bypass:** ✅ `POST /api/auth/unlock` clears the lockout of any
   *non-admin* account with **no code, no login, nothing** — anyone can defeat the
   3-attempt lockout and keep brute-forcing (`src/app/api/auth/unlock/route.ts`).
   (Admin accounts at least require the master code — but see #4.)
6. **Password-reset discloses accounts + orphans tokens** 👀
   (`request-password-reset/route.ts`): returns 404 "No account is registered with that email"
   (user enumeration), and creates a 10-min reset token in the DB *before* discovering SMTP
   isn't configured (503) — validity window starts with no email ever sent.

## 🟠 FUNCTIONAL BUGS

7. **`/api/auth/lock-status` never reports a locked account.** ✅ Missing
   `export const dynamic`/`runtime`, so Next.js prerendered it as a **static** route
   (build output: `○ /api/auth/lock-status`) — it always returns `{"locked":{}}` from build time.
   Reproduced: after locking `encoder` (login said `locked:true, 900s`), lock-status returned `{}`.
   Both `LoginPage.tsx:79` and `UserManagementModule.tsx:320` poll this broken endpoint.
8. **Lockout is in-memory only** 👀 (`src/lib/lockout.ts`): `Map` resets on every server
   restart/redeploy; not shared across instances.
9. **Activity log attribution is fake:** 👀 most mutations hardcode
   `user: 'admin'` (maintenance, inspections DELETE/PATCH, local-road) regardless of who acted;
   since there's no session, it can't be fixed without finding #1.
10. **`database-schema.sql` is out of sync** 👀 with the real schema auto-created in
    `local-database.ts` — missing `password_reset_codes`, `password_reset_tokens`,
    `activity_logs` tables. The doc file describes only 4 of 7 tables.
11. **`purgeExpiredArchives()` runs on every DB access** 👀 (`local-database.ts:35-40`):
    a write transaction on every API call (perf/DB-locking risk, and deletes during reads).
12. **Data is fetched before login** 👀 — `App.tsx` loads all roads/inspections/maintenance
    on mount regardless of `isLoggedIn` (works only because of finding #2).

## 🟡 CODE HYGIENE / MINOR

13. Dead code: `src/main.tsx` (Vite entry — Next.js never uses it), `src/styles/*`
    (2 empty files), unused `SystemArchitecture.tsx` and `ReportsModule.tsx` (never imported).
14. `/api/health` hardcodes `environment: 'development'` 👀 even in production.
15. No ESLint config — `npm run lint` drops into an interactive setup prompt, so linting can't run in CI.
16. Default sender email personal address hardcoded (`request-password-reset/route.ts`: `ortegajeicelmae@gmail.com` fallback).
17. Inactive-user check in login happens **after** password verification, and failed
    attempts against an *inactive* account still count toward lockout (minor).

## ✅ What is actually fine
- TypeScript `strict` passes; production build passes (17 routes).
- Passwords are hashed properly (`scrypt` + per-user salt, `timingSafeEqual`).
- Password-reset tokens/codes stored hashed, 10-min expiry, 5-attempt cap on codes.
- SQL uses prepared statements (no SQL injection found); most inputs are validated.

> ⚠️ Scope note: fine for an **academic/demo** project (README says so). Findings #1–#6
> would be blockers for any real deployment with real municipal data.
> All test artifacts created during this audit (road `AUDIT-TEST-ROAD`, user
> `intruder@test.local`, SQLite DB, `.next`) were in gitignored paths and have been deleted.
